# Stage 10R.7A-TX — Root Cause Investigation Report

**Status: RESOLVED.** The root-cause investigation below (unchanged from when it was accepted) was followed by an approved fix — see "Resolution" at the end of this document for what actually shipped, why, migration impact, and before/after proof. Not committed, not pushed, 10R.7B not started, pending final sign-off — the fix itself is implemented and fully tested.

## Bottom line, up front

**`TransitionPhaseUseCase`'s scratch-context architecture is not the cause of the failure, and is not implicated by any evidence gathered.** The corruption is a SwiftData/CoreData framework-level defect: when two `Exercise` rows share the same `@Attribute(.unique) canonicalName` value and each is referenced by a real `ExerciseSlot.resolvedExercise` relationship (an un-inversed to-one relationship), the uniqueness-constraint-conflict resolution that runs on the second `save()` corrupts an unrelated `Exercise` row (all required scalar fields become `nil`), which then fails NSManagedObject validation. This was proven directly, with zero scratch context and zero `TransitionPhaseUseCase`/`StartPhaseUseCase` involvement in the minimal case, and then proven again using the exact real production call sequence (`ExerciseCatalog.makeAndInsert` → `AcceptStrategicPlanUseCase` → `StartPhaseUseCase.start`) called twice against the same store while explicitly never invoking `TransitionPhaseUseCase` at all.

The precipitating condition — two `ExerciseCatalog.makeAndInsert` calls against the same store — is a **test-fixture-only** scenario. `SeedAnmualPlanJourney`'s real-world caller (`TrainingOSApp.init`) guards against ever seeding twice (`existingUserCount == 0`), and no production code path other than `ExerciseCatalog.makeAndInsert` ever constructs a new `Exercise` object (confirmed by exhaustive grep — see item 6). So the specific failing test (`AnnualPlanSeedDateTests.testASecondSeedInvocationNeverDeletesTheFirstRunsData`) is exercising a scenario ("call the whole seed journey twice") that cannot occur in real single-seed production use, but the underlying SwiftData defect it surfaces is real and would recur any time two Exercises legitimately end up sharing a `canonicalName` while both are relationship-referenced — independent of seeding, transitions, or scratch contexts.

## Answers to the mandated 15 items

**1. Smallest reliable reproduction.**
Toy model, 12 lines: an entity with one `@Attribute(.unique)` string property, and a second entity with a plain (non-unique, un-inversed) to-one relationship to the first. Insert+save entity A (name "X"), attach it to relationship R1, save. Insert entity B (name "X", same unique value, different identity), attach it to relationship R2, save. The second save throws `NSCocoaErrorDomain Code=1560` with the *third*, unrelated object's required scalar fields all reported `nil`. Reproduces 100% of runs, with zero SwiftData features beyond `@Attribute(.unique)` + one un-inversed to-one relationship + two sequential saves.

**2. First operation that introduces corruption.**
The **second** `context.save()` — specifically, the one that persists a *second* row whose `@Attribute(.unique)` value collides with an already-saved, already relationship-referenced row. The corruption is not present in memory before that save; it manifests only inside CoreData's own save-time constraint-conflict resolution.

**3. Exact root cause.**
SwiftData's `@Attribute(.unique)` is implemented as a CoreData uniqueness constraint. When a second object violates that constraint against an existing, persisted object, CoreData's store resolves the conflict at save time by merging/replacing the conflicting rows rather than throwing a duplicate-key error (confirmed empirically: Rung0b / Toy A, with no relationship at all, silently merge to one row with no error). When one of the two colliding objects is the destination of an un-inversed to-one relationship, CoreData has no way to walk backward from the object being merged/dropped to the relationship(s) pointing at it (there is no inverse to traverse), so it cannot correctly repair or cascade that relationship as part of the merge. The result is a corrupted, orphaned managed object — all required scalar attributes nil, only the empty-array-encoded properties intact (`{length = 2, bytes = 0x5b5d}` = `"[]"`) — that then fails the save's own validation pass with "is a required value" on every scalar field. The `"CoreData: annotation: repairing missing delete propagation for to-one relationship resolvedExercise ... with bad fault"` log line is CoreData's own diagnostic for precisely this situation: a to-one relationship whose destination was invalidated by a merge/delete it had no inverse-relationship path to clean up correctly.

**4. Whether `@Model` crosses contexts.**
No, not in the minimal reproduction (Toy A/B/C, Rung0/0b/0c/0d/0e all use exactly one `ModelContext` throughout) — this rules out cross-context `@Model` reuse as a *necessary* cause of this specific corruption. Separately, I re-read the real `TransitionPhaseUseCase.swift` in full: `outgoingPhase`/`nextPhase`/`nextMix` are all re-fetched into the scratch context by `persistentModelID` before use (lines 128–148); `materializationContext.strengthCandidateExercises`/`functionalFitnessCandidateExercises` are explicitly re-fetched by `persistentModelID` into the scratch context (lines 181–191) with an inline comment documenting the exact cross-context fatal this was written to avoid. No `@Model` object originating in the caller context is ever assigned as a relationship value inside the scratch graph in the current code — the invariant the directive asked me to verify holds, as written, for everything `TransitionPhaseUseCase` itself touches.

**5. `ExerciseSlot.resolvedExercise` ownership findings.**
`resolvedExercise: Exercise?` (`ExerciseSlot.swift:62`) is a plain to-one relationship with **no inverse**, explicitly documented in-code as sharing "the same documented, deferred risk" as `ExercisePrescription.exercise` (`DELETE_RULE_MATRIX.md`). This is exactly the ingredient that converts a silent, harmless uniqueness-merge (Rung0b: no relationship, no corruption) into a validation-failing save (Rung0d/0e: same duplicate names, plus a real `resolvedExercise` relationship, corruption). Exercises are meant to be canonical/shared catalog entities referenced by ID, never duplicated — the assumption `resolvedExercise` was written under (a single canonical row per exercise, ever) is the assumption `ExerciseCatalog.makeAndInsert`'s non-idempotency violates. No materializer caches `Exercise` `@Model` references across catalog calls; `ExerciseCatalog` itself does not return context-bound objects reused across separate `makeAndInsert` invocations — each call is a fully independent, fully fresh construction (which is itself the actual defect — see item 6).

**6. Catalog/cache findings.**
`ExerciseCatalog.makeAndInsert(context:)` unconditionally constructs ~38 brand-new `Exercise(...)` objects with fixed, hardcoded `canonicalName` strings (e.g. `"Barbell Bench Press"`) on every call, and `context.insert()`s all of them — it never fetches-or-creates by name, never checks for an existing row. I grepped every non-test, non-`ExerciseCatalog` production source file for `Exercise(` constructor calls (`grep -rn "Exercise(" TrainingOS/Application TrainingOS/Engines TrainingOS/Domain`, filtered to real constructor sites) and found **zero** — no materializer, resolver, or use case anywhere in `Application/`, `Engines/`, or `Domain/` ever constructs a new `Exercise`. `findCatalogedExercise(named:context:)` (`HypertrophyProgramGenerator.swift:1006`) is the one place that resolves an exercise by name, and it is purely a read-only `FetchDescriptor` — it never inserts and cannot itself cause corruption, though with duplicate-named rows present it would non-deterministically return whichever duplicate `.first` happens to surface, which is the likely explanation for the previously-observed run-to-run variance in the original bug's specific symptom (`stimulusValidationFailed` vs. a nil-fields crash — same underlying corrupted state, different exercise resolved to first depending on fetch ordering). No static/shared arrays of `@Model` instances, no singleton catalogs, no capturing closures over `Exercise` objects exist in production code.

**7. Caller-context stale-object findings.**
Not implicated. Rung0d and Rung0e both reproduce the corruption using a **single** `ModelContext` from start to finish — there is no scratch context, no sibling context, and therefore no possibility of "the caller context still holding a stale object from an earlier scratch save" contributing to what was observed. This was a reasonable leading hypothesis given `TransitionPhaseUseCase`'s architecture, but it is empirically ruled out as a necessary cause here. (`TransitionPhaseUseCase`'s own caller-side refresh-by-ID code, lines 218–237, was independently re-read and is a plain re-fetch of each object by `persistentModelID` after `scratchContext.save()` — this is the same pattern Stage 10R.6 already validated and is not implicated either.)

**8. Seed-specific findings.**
`SeedAnnualPlanJourney.seed` does not reuse, query-by-name, or intentionally share canonical Exercises across separate seed runs — each call gets its own fresh `ExerciseCatalog` (because each call's caller, per the existing test, constructs a new `ExerciseCatalog.makeAndInsert(context:)` before calling `seed`). It never deletes or mutates existing rows; it only ever inserts. The failing test's "call `makeJourney()` twice" pattern is an explicit, deliberate worst-case probe of "what if a caller re-seeds" — the test's own comment says as much ("even in the worst case where a caller mistakenly re-seeds... the real guard in `TrainingOSApp` prevents this from ever happening in production"). Per the directive, I have **not** dismissed this as unrepresentative merely because production seeds once: the corruption signal is real and still needs explaining, and it now is — but I can also report, with the evidence in hand, that the specific *precondition* (two `ExerciseCatalog.makeAndInsert` calls against the same store) genuinely cannot occur via any real, single-seed, single-`TrainingOSApp`-launch production path, because no other code constructs new `Exercise` rows (item 6) and the app-level guard prevents `seed` itself from running twice.

**9. Why Stage 10R.6 did not expose this.**
Every Stage 10R.6 test builds exactly one `ExerciseCatalog` per test (a fresh in-memory container per test, one `makeAndInsert` call per test) — no 10R.6 test ever calls `ExerciseCatalog.makeAndInsert` twice against the same context/store. Since the corruption's necessary precondition is two colliding-`canonicalName` `Exercise` rows both attached to a real `resolvedExercise` relationship, and 10R.6's own repeated-rollforward tests only ever re-use the *same* already-existing Exercises (never construct new ones), the trigger condition never arose in any 10R.6 scenario. This has nothing to do with 10R.6's tactical-materialization content being different in kind from 10R.7's strategic-transition content — it is purely about whether `ExerciseCatalog.makeAndInsert` was ever called more than once per store, which 10R.6 never did and this one specific 10R.7 test (by design, deliberately) does.

**10. Is the current `TransitionPhaseUseCase` unsafe in real production?**
No, not via this mechanism. `TransitionPhaseUseCase`/`StartPhaseUseCase` never construct new `Exercise` rows (item 6) — every real strategic transition only ever *relates* already-existing, already-canonical Exercise objects (refetched by ID into the scratch context, item 4) to newly-created `ExerciseSlot`s. Since the corruption strictly requires a second `Exercise` row colliding on `canonicalName`, and nothing in the real transition path can produce one, real repeated strategic transitions (phase1→phase2→phase3...) cannot trigger this specific defect. I found no other cross-context or object-ownership defect in `TransitionPhaseUseCase` during this audit — the invariant "no caller-context `@Model` is used as a relationship object in the scratch graph" holds throughout the file as written.

**11. Recommended architecture (A/B/C/D/E).**
None of the five apply — the premise of the menu (that the scratch-context transaction boundary itself might be structurally unsafe) is not supported by any evidence gathered; the current scratch-context design (closest to "Architecture B": scratch context + explicit ID-based refetch at the boundary, nothing passed in as a raw cross-context `@Model`) should be **kept as-is**. The actual, separate defect that needs fixing lives outside `TransitionPhaseUseCase` entirely, in two places: (a) `ExerciseCatalog.makeAndInsert`'s non-idempotent construction (test/seed-fixture code, not production business logic), and (b) `ExerciseSlot.resolvedExercise`'s missing inverse (a pre-existing, already-documented deferred risk, not something introduced by 10R.7A). Fixing either one independently would prevent this specific test failure; the un-inversed-relationship risk is the more fundamental of the two since it's what turns *any* future uniqueness collision (not just this test's contrived one) into a hard corruption rather than a silent merge.

**12. Exact proposed code changes.**
None implemented, per explicit instruction ("STOP. Do not implement the fix yet"). For the record, once authorized, the two independent candidate fixes are: (a) make `ExerciseCatalog.makeAndInsert` fetch-or-insert each exercise by `canonicalName` instead of unconditionally constructing a new row every call (a test/seed-fixture-only change, does not touch production business logic), and/or (b) give `ExerciseSlot.resolvedExercise` (and its documented sibling `ExercisePrescription.exercise`) a proper inverse relationship so CoreData can correctly cascade a uniqueness-constraint merge instead of leaving an orphaned fault — this is a schema/model change with delete-rule and migration implications beyond this investigation's scope and should be its own scoped decision, not bundled into this fix.

**13. Tests required for the fix (once authorized).**
Do not weaken or skip-convert `AnnualPlanSeedDateTests.testASecondSeedInvocationNeverDeletesTheFirstRunsData` — it must keep failing until whichever fix is chosen actually resolves it, then pass unmodified. Add a new, permanent unit test asserting `ExerciseCatalog.makeAndInsert`, called twice against the same context, never creates duplicate-`canonicalName` rows (a direct regression test for item 6's finding). If the `resolvedExercise` inverse is added, add a regression test exercising a uniqueness collision under a relationship to confirm CoreData now handles the merge cleanly instead of corrupting (a permanent version of Rung0d).

**14. Do any accepted 10R.7A semantics need to change?**
No. Nothing in this investigation implicates `TrainingPhaseCompletion`, `StartNextHypertrophyMesocycleUseCase`, the `primaryInstance`/`secondaryInstances` redefinition, or any other 10R.7A lifecycle semantic. The scratch-context correctness of `TransitionPhaseUseCase` itself stands as implemented.

**15. Unresolved uncertainty.**
The precise SQLite/CoreData-internal algorithm that performs the uniqueness-constraint merge and produces a *third*, wholly-unrelated phantom row (rather than, say, failing on one of the two actual colliding objects) is not directly observable from outside the framework — I have inferred it from Apple's documented uniqueness-constraint conflict-resolution behavior, the "repairing missing delete propagation... bad fault" diagnostic, and the consistent empirical shape of the failure (nil scalars, intact empty-array-encoded properties) across every real reproduction. I cannot cite Apple's private implementation to confirm this mechanistically beyond that; if fully authoritative confirmation is required, it would need a filed feedback/reproduction with Apple or inspection of the on-disk SQLite store's row-level changes across the failing save, which was not attempted here as it goes beyond what's needed to identify a concrete, actionable root cause.

## Explicit disposition of hypotheses A–I

- **(A) scratch ModelContext itself unsafe** — ruled out. Reproduces with zero scratch contexts (Rung0d, Rung0e).
- **(B) passing/reusing `@Model` objects across contexts** — ruled out as cause of *this* corruption (single-context repro); separately confirmed absent in the real `TransitionPhaseUseCase` code (item 4).
- **(C) relationships assigned using objects fetched/created in another context** — ruled out for the same reason as B.
- **(D) stale registered/cached objects in the caller context after a sibling-context save** — ruled out; no sibling context exists in the minimal or Rung0e repro.
- **(E) relationship delete/inverse semantics** — **confirmed as a necessary ingredient.** `resolvedExercise` has no inverse; this is exactly what prevents CoreData from cleanly cascading the uniqueness merge.
- **(F) seed-specific behavior that incorrectly destroys/replaces objects** — **confirmed, refined**: not destructive, but non-idempotent construction (`ExerciseCatalog.makeAndInsert`) is the precipitating trigger.
- **(G) persistent-history/container behavior** — no evidence found; not exercised by any reproduction, no anomalous container-level behavior observed.
- **(H) StartPhase/materializer code holding Model references beyond the owning context** — no evidence found; grep confirms no production code retains `Exercise` `@Model` references across calls.
- **(I) combination** — yes: **E + F together** are necessary and sufficient. Neither alone reproduces (Rung0b: F without a relationship → passes; no code path exercises E without F ever occurring, since a relationship alone to a single canonical Exercise is completely safe, as literally every other passing test in the suite proves).

## Resolution (Stage 10R.7A-TX-FIX)

The investigation above was accepted as-is; this section records what was actually fixed, chosen from the recommendation in item 12.

**Chosen fix — both halves, matching the E + F combination (item I) that was necessary and sufficient to reproduce the defect:**

1. **`ExerciseCatalog.makeAndInsert` → `ExerciseCatalog.resolveOrInsert`** (`TrainingOS/Application/Seed/ExerciseCatalog.swift`). The internal `make(...)` helper now fetches an existing `Exercise` by `canonicalName` first and only constructs+inserts a new row if none exists; the alias-attachment helper (`addAliasIfMissing`) is likewise idempotent (skips an already-attached `sourceName`). Every call site (`SeedDataProvider.swift`, `DebugAcceptanceFixturesUseCase.swift`, and every test file) was renamed to match — a mechanical rename, not a behavior change at any call site. **Why this is the correct domain behavior, not a workaround:** the domain concept was never "construct N fresh Exercise objects" — it was always "make sure the canonical catalog exists in this context," which `DebugAcceptanceFixturesUseCase.reconstructExerciseCatalog` already had to hand-implement separately (fetch-by-name) because the old `makeAndInsert` couldn't be safely called a second time. The rename makes the real, always-true invariant ("a given store has exactly one canonical row per `canonicalName`, ever") the actual contract of the API, instead of an accident of it only ever being called once in practice.

2. **`ExerciseSlot.resolvedExercise` gained its required inverse**: `Exercise.resolvedSlots: [ExerciseSlot]` (`.nullify`, `TrainingOS/Domain/Entities/Exercise.swift`), documented in `DELETE_RULE_MATRIX.md`'s new "Stage 10R.7A-TX addition" section. `resolvedExercise` itself is unchanged — same plain-`var` single-sided-ownership convention as every other inverse relationship in this codebase (`SlotSelectionOverride.templateSlot`, `ExercisePrescription.sourceExerciseSlot`, etc.). **Why `.nullify`, not `.cascade`:** a canonical Exercise is shared catalog data referenced by many slots at once by design (proven by `RelationshipOwnershipTests.testMultipleExerciseSlotsCanReferenceTheSameCanonicalExercise`) — it is never owned by any one slot, so a slot's deletion must never touch it, and nothing in this app deletes a canonical Exercise out from under active slots today. Fixing only the catalog (idempotent construction) without this would still leave the underlying SwiftData sharp edge live for any other future path that legitimately produces two same-`canonicalName` Exercises; fixing only the inverse without the catalog would leave `ExerciseCatalog` non-idempotent and still capable of creating the collision in the first place. Both were required.

Nothing else was touched: `TransitionPhaseUseCase`'s scratch-context architecture, `TrainingPhaseCompletion`, `StartNextHypertrophyMesocycleUseCase`, calibration semantics, and every other frozen item from the investigation directive are unmodified.

**Schema/migration impact:** `PersistenceController.swift` declares one flat, unversioned `Schema([...])` (no `SchemaMigrationPlan`) — adding `Exercise.resolvedSlots` is a schema change with no existing migration plan to slot into, by design (this project has none yet, consistent with its pre-release stage). This was not left as untested theory: a standalone script (`migration_old_schema.swift`/`migration_new_schema.swift`, real `@Attribute(.unique)` + relationship shapes matching production) wrote a real on-disk store under the pre-fix schema (no inverse), then reopened that exact file under the post-fix schema (with `Exercise.resolvedSlots` declared). It opened with **zero errors**, and the inverse collection was correctly and automatically populated from the existing `resolvedExercise` foreign-key data already on disk — no explicit migration code needed, confirming SwiftData's automatic lightweight migration handles this purely-additive relationship change cleanly. A `simctl`-based attempt to reproduce this on an installed Simulator app was also made; `xcrun simctl install` was found to reallocate a fresh Data container on reinstall in this environment rather than reliably preserving one (a CLI-tooling limitation, not a finding about the app), so that specific attempt wasn't conclusive on its own — the standalone script above is the decisive proof. There is no production user store at this stage of development (CLAUDE.md scope), so even in the unlikely event a real device's local store ever failed this migration, the existing `fatalError` in `PersistenceController.makeAppContainer` would surface it immediately and loudly, and the fix would simply be deleting the local dev/simulator store — no migration framework was built, per instruction not to build one unless actually necessary.

**Before/after reproduction result:** every reproduction from the investigation above now passes cleanly against the fixed code — see the Stage 10R.7A implementation report (`STAGE10R7A_IMPLEMENTATION_REPORT.md`) for the full targeted/full-suite/repeated-run/Simulator results.
