Implementation specification · v1.0 · 13 August 2026

Training OS

Developer handoff for the iPhone training application approved across design passes 01–05. This document translates the approved product into an implementation specification. It adds no product features.
Locked decisions — do not revisit without the product owner
Navigation: three tabs — Today / Plan / Progress. Programs inside Plan, Profile from the Today header.
Hierarchy: Day → Session → ordered WorkoutBlock → Movement → Prescription → Recommendation → Result.
RIR: engine owns target, user owns actual, stored per set, preselected at target.
Schedule: the engine recommends automatically; the user approves anything affecting future sessions.
Deload: program-owned week inside a mesocycle. Recovery / Transition are planner-level phases.
Scaling: remembered in the Performance Profile, offered, never assumed.
Planning: strategic beyond four weeks, tactical within. Two entry paths — guided, or program-first.
Imported programs: Strict by default; the model carries Adaptive from V1 even if unimplemented.
Universal pattern: event → engine recommendation → reason → user approval.
Tonnage: stored, never surfaced as a measure of training quality.

1 · Product architecture

Six subsystems with one direction of flow. The user chooses the destination; the planner defines the route; programs supply methodology; the profile is permanent memory; the progression engine is the only component permitted to produce a target; execution is the only component permitted to produce a result.

Subsystem Owns Must never
Goal & Long-Term PlannerDestination, phases, priorities, frequency, program selection, interference rulesEmit individual sets or loads
Program EngineProgramDefinition: weeks, blocks, prescriptions, progression rules, substitutionsHold user performance data
Performance ProfileEvery set performed, canonical exercise IDs, PRs, estimates, recency confidence, scaling history, name mappingsBe scoped to one program
Progression EnginePrescription + Profile + latest results → Recommendation + reason codeReturn a value without a reason code
ExecutionSession running, timers, set entry, scoring, result captureRequire a network connection
HealthKit IntegrationReads body metrics and HR; writes completed workoutsBe the source of truth for training

Results write back to the Performance Profile permanently, and independently of the program that produced them.

3 · State model

Session   SCHEDULED → IN_PROGRESS → COMPLETED
                    ↘ SKIPPED · MISSED (derived when the day passes)
                    ↘ ABANDONED (started, never finished)
Block     PENDING → ACTIVE → COMPLETED · SKIPPED
Phase     PLANNED → ACTIVE → COMPLETED · PAUSED · ABANDONED
Plan      DRAFT (proposal, nothing saved) → ACTIVE → SUPERSEDED
Import    PARSING → VALIDATING → AMBIGUITY_REVIEW → CONFIRMED → COMMITTED
                  ↘ FAILED (source unreadable, nothing written)

MISSED is derived, never stored as an event by itself: a SCHEDULED session whose day has passed. The reflow proposal is generated on next app open, not by a background job, so the user is never told about changes made while they were away.

6 · Interaction specifications

Set logging
Weight and reps use ± steppers at the user's equipment increment. RIR arrives preselected at the prescribed target; confirming logs the set in one tap. Tapping a different RIR chip is the only extra interaction, and actualRir is persisted per set regardless. Long-press a value for keypad entry. Rest timer starts on log, runs in the background, and fires a local notification.
AMRAP
Countdown clock plus one full-width round target occupying the remaining height; a single tap anywhere on it increments rounds. Undo is a small secondary control. Extra reps are requested once, after time expires, never during the effort. Final score is rounds + extraReps.
EMOM
Dominant per-minute countdown. The movement advances automatically; NEXT is always visible. A three-second pre-cue and a minute-change cue fire as tone plus haptic, so the screen need not be watched. Marking a minute incomplete is optional and reversible. No interaction is required to complete the block.
For Time
Elapsed clock with optional splits. Round checkboxes are large targets. Passing the cap turns the clock amber and records cappedAt without stopping the timer. Scaling choice is shown before the first rep and recorded with the result.
Recommendation explanation
Any recommended value is tappable and opens a sheet stating the reason in plain language, then the reason code, prescription, previous performance, increment used and confidence with its age. Every engine output must be explainable this way; a recommendation without inputs to display is a bug.
Approval sheets
Reflow, re-entry and plan proposals share one pattern: what happened, the recommendation as concrete before-and-after, the reason code, two or three alternatives, then Accept and a dismissal that changes nothing. Nothing is written on dismissal.

7 · Progression engine contract

recommend(input) → Recommendation

input:  { prescription, progressionRule, performanceRecord,
          recentResults[], equipmentIncrement, adherenceMode }
output: { value, reasonCode, inputs{}, confidence }

Pure, deterministic and side-effect free. Same inputs must always yield the same output — this is what makes the Why sheet trustworthy and the engine testable. No AI in V1. Rules live in configuration, not in view code.

Reason code Condition
LOAD_INCREASETop of rep range hit on every set at or above target RIR
REP_INCREASEIn range but below the top; load holds, reps advance
DOUBLE_PROGRESSION_INCOMPLETESome sets reached the top, others did not
HOLDRepeat the same prescription; a set fell below range
LOAD_DECREASERepeated failure to reach the bottom of the range
DELOAD_PRESCRIBEDProgram-owned deload week is active
PERCENTAGE_OF_ESTIMATEProgram prescribes a percentage; value derived from e1RM
CALIBRATION_REQUIREDNo usable history; open with a calibration set, not a guess
RECENCY_DECAYHistory exists but is old; confidence reduced, never deleted
SUBSTITUTION_ESTIMATEValue inferred from a related movement in the same group

8 · Planning engine contracts

proposePlan(goal, availability, profile)          → PlanProposal   [PLAN_FROM_GOAL]
proposePhaseForProgram(programDef, goal, avail)   → PlanProposal   [PHASE_FROM_PROGRAM]
recommendProgram(phase, availability, profile)    → ProgramRecommendation
fitCapacity(availability, requiredSessions)       → CapacityFit    [CAPACITY_FIT]
materialiseTacticalWeeks(phase, fromDate, weeks)  → Session[]
proposeReflow(missedSession, phase, availability) → ReflowProposal [MISSED_SESSION_REFLOW]
proposeReturn(absence, profile, phase, program)   → ReturnProposal

Every proposal is a DRAFT value object. Nothing is persisted until the user accepts. materialiseTacticalWeeks is the only function that creates Sessions, and it runs for the four-week horizon only — configurable, defaulting to 4.

Capacity. Availability describes opportunities — training days per week, minutes per day, whether doubles are acceptable, whether an occasional longer session is possible. The planner derives how many Sessions fit. Seven sessions across five training days is a valid fit when doubles are allowed.

Priority. Derived from the active Phase type: Muscle Gain and Strength phases give strength priority; endurance phases give the endurance modality priority; Functional Fitness gives mixed-modal priority. It is never presented as a question during planning. A manual override exists under Profile → Advanced.

Re-entry. proposeReturn considers time away, modality, Performance Profile confidence, prior training history, program rules, and optionally user-reported readiness. It returns one of CONTINUE, RETURN_REDUCED_LOAD, RETURN_REDUCED_VOLUME, RETURN_REDUCED_LOAD_AND_VOLUME. V1 uses conservative deterministic thresholds held in configuration and displayed in the approval sheet. No specific figure — including the 90%-load example in the designs — is product logic.

9 · Program import architecture

Source file → Parser → Intermediate Program Representation → Validation
           → Ambiguity Review → Canonical Program Model → Program Engine

Hard rule. Interpreted or AI-assisted content is never written directly into the Canonical Program Model. Every path to the canonical model passes through Validation and, where confidence is insufficient, Ambiguity Review.

Source file
Stored verbatim and immutable. Re-import must be possible after a parser improvement without asking the user for the file again.
Intermediate Program Representation
Every node carries a SourceRef — sheet, cell or range, plus the original formula text. Every canonical prescription must be traceable back to the cell that produced it, and that trace is retained after commit.
Validation
Schema conformance, plausible ranges, referential integrity, week and block completeness, exercise resolution. Produces errors that block commit and warnings that do not.
Ambiguity Review
Anything below the confidence threshold is presented for confirmation with its source location shown. Guessing is prohibited. The user can defer an ambiguity; the affected prescription then falls back to a stated default and remains flagged.
Canonical Program Model
A ProgramDefinition of structured rules. Percentages, rep ranges, RIR and RPE targets, progression conditions, deload logic and substitution options survive as executable rules — never flattened into static workouts. The Progression Engine executes the methodology; it does not replay the spreadsheet.

Adherence mode. adherenceMode: STRICT | ADAPTIVE on ProgramDefinition, with STRICT the default. STRICT follows the imported methodology exactly unless the user explicitly changes it. ADAPTIVE preserves intent, progression model and stated constraints while permitting a declared set of planner adjustments. V1 implements STRICT; the model, the migration path and the UI copy must accommodate ADAPTIVE without a schema change. Immutability is a default, not an architectural assumption.

10 · Canonical exercise model

source name → proposed canonical exercise ID → confidence → user confirmation
                                                        → mapping remembered

“DB Incline”, “Incline DB Press” and “Incline Dumbbell Press” all resolve to one canonical exercise, so one history serves them all. Resolution runs alias table first, then normalised string match, then movement-pattern heuristics. High confidence resolves silently; anything below the threshold goes to Ambiguity Review with the source cell shown and the option to create a new canonical exercise instead.

Confirmed mappings are stored against the user's profile and applied to future imports automatically. A canonical exercise carries modality, equipment, movement pattern and substitution groups; substitution groups are what make SUBSTITUTION_ESTIMATE possible. All performance data references canonical IDs only — never source strings.

Permissions are requested per type, in context, at the moment the data would first be useful — never as an onboarding wall. Programs, sets, reps, weight, RIR, PRs, progression, phases and planning are owned by this app's store in all cases. No session, block or recommendation may be blocked by a missing Health permission.

12 · Offline-first architecture and persistence

The local store is authoritative. Execution — timers, set entry, scoring, block completion, session completion — must work with no network, and progression recommendations for materialised sessions must be computed locally. Sync is a background reconciliation, never a precondition.

Local store   SwiftData / Core Data — full domain model
Write path    optimistic local write → outbox entry → sync → ack
Conflicts     SetResult and BlockResult are append-only, last-writer-wins
              per record; plans and phases resolve server-authoritative
              after a user-visible notice
Timers        wall-clock anchored (startedAt + offset), never tick counts,
              so backgrounding, lock and app kill cannot drift the score
Recovery      an interrupted Session resumes at its last completed block;
              in-flight set entry is restored from local draft state
Retention     source import files and IPRs retained for re-import;
              nothing in the Performance Profile is ever hard-deleted

Multi-user on one device is supported by scoping every query to userId; there is no shared performance state.

13 · Reason-code taxonomy

Every engine output carries a code. Codes are stable identifiers, are never shown as the only explanation, and always appear alongside plain-language copy. Grouped by prefix:

Progression   LOAD_INCREASE · REP_INCREASE · HOLD · LOAD_DECREASE
              DOUBLE_PROGRESSION_INCOMPLETE · DELOAD_PRESCRIBED
              PERCENTAGE_OF_ESTIMATE · CALIBRATION_REQUIRED
              RECENCY_DECAY · SUBSTITUTION_ESTIMATE
Planning      PLAN_FROM_GOAL · PHASE_FROM_PROGRAM · CAPACITY_FIT
              INTERFERENCE_CONFLICT · MISSED_SESSION_REFLOW
              PHASE_SHIFTED · WEEK_VOLUME_PRESERVED
Re-entry      CONTINUE · RETURN_REDUCED_LOAD · RETURN_REDUCED_VOLUME
              RETURN_REDUCED_LOAD_AND_VOLUME
Import        SOURCE_UNREADABLE · SCHEMA_INVALID · RANGE_IMPLAUSIBLE
              FORMULA_UNRESOLVED · EXERCISE_UNRESOLVED
              EXERCISE_AMBIGUOUS · MULTIPLE_MOVEMENTS_IN_CELL
              DEFERRED_WITH_DEFAULT

Codes are additive. New codes may be added; existing ones must not be renamed or repurposed, because stored recommendations reference them historically.

Sync conflict on a planUser is told what changed before it is applied.

15 · Accessibility requirements

Dynamic Type supported through the largest accessibility sizes; timer and set-entry layouts must reflow rather than clip or truncate. Minimum hit target 44 × 44 pt — the AMRAP round target and EMOM controls are far larger by design. Contrast at least 4.5:1 for body text and 3:1 for large text in both dark and light modes. Every interactive element carries an accessibility label and a value where it has one; steppers expose increment and decrement actions. Timer state changes are announced, and interval cues are delivered as sound and haptic as well as visually, so no cue is visual-only. VoiceOver order follows visual order. Reduce Motion removes the pulse and transitions without removing information. Colour is never the sole carrier of meaning: PRs, off-target RIR and missed days all carry text or shape as well.

16 · Test strategy

Engine unit tests are the priority. The Progression Engine is pure, so every reason code gets a table-driven case, including boundaries: exactly at the top of the range, mixed sets, a single below-range set, stale history at the decay threshold, missing history, and percentage prescriptions against a fresh estimate. Same inputs must always produce the same output and reason code.

Planning tests cover capacity fitting (7 sessions into 5 days with doubles allowed and disallowed), interference rules, reflow options preserving weekly volume, phase shifting against a fixed target date, and the four re-entry outcomes at their threshold boundaries.

Import tests run a corpus of real spreadsheets as golden files: parser output, IPR with SourceRefs intact, validation results, and the exact set of ambiguities raised. A regression here is a silent data-integrity failure, so the corpus must include known-bad files that must fail rather than guess.

Execution tests cover timer accuracy across backgrounding, lock and app kill; block state transitions; offline logging with later sync; and interrupted-session recovery.

UI tests cover the five journeys end to end, plus Dynamic Type at the largest size and VoiceOver traversal on Today, set logging, AMRAP and the approval sheets.
